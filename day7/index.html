Read-heavy system

SnapShare is read-heavy: users generate roughly 50 feed reads for every upload. The design therefore prioritizes low-latency reads with a CDN, cache, horizontally scalable app servers, and a database read replica. Upload work can be buffered and processed asynchronously.

Why object storage?

Large photo files should not live inside the database because they make storage, backups, replication, and queries more expensive. Object storage holds the originals and thumbnails, while the database stores compact metadata and storage keys.

CDN

Serves popular photos and thumbnails close to users, reducing latency and origin traffic.

Load balancer

Distributes requests across healthy app servers and supports horizontal scaling.

App servers

Handle authentication, validation, feed logic, and upload coordination while remaining stateless.

Cache

Keeps hot feeds and metadata in memory so repeated reads avoid database work.

Primary database

Stores durable users, follows, photo metadata, and upload records and handles writes.

Read replica

Handles feed and metadata reads without competing with primary database writes.

Object storage

Stores large originals and generated thumbnails durably and independently of database records.

Queue

Buffers thumbnail jobs so uploads stay responsive during worker slowdowns or traffic bursts.

Thumbnail worker

Creates thumbnails, stores them, and updates the related photo metadata.

Photo upload flow

  1. The user selects a photo and starts an upload request.
  2. The app server authenticates the user, validates the file, creates a photo ID, and reserves a storage key.
  3. The client uploads the original directly to object storage using a short-lived upload URL.
  4. The app server records the photo metadata and original object key in the primary database.
  5. The app server places a thumbnail job on the queue and returns upload success.
  6. A thumbnail worker reads the original, creates the 50 KB thumbnail, and stores it in object storage.
  7. The worker saves the thumbnail key and processing status in the database; feed requests then use CDN URLs.
  8. Failed jobs are retried, with repeatedly failing jobs sent to a dead-letter queue for investigation.

Trade-offs

Direct upload vs app-server upload

Benefit: Direct uploads reduce app-server bandwidth. Cost: They require signed URLs, completion handling, and validation after upload.

Read replica vs one database

Benefit: Read replicas increase feed capacity. Cost: Replication lag can delay newly uploaded photos in some feeds.

Async vs synchronous thumbnails

Benefit: Async processing makes uploads faster and absorbs bursts. Cost: Users may briefly see a processing placeholder.

Cache performance vs freshness

Benefit: Caching lowers latency and cost. Cost: Updates and deletions require invalidation and may briefly show older data.
